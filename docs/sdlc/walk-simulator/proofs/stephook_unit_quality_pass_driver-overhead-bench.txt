STATIC ACCOUNTING (every line the diff adds inside the tick-loop call graph: startDriver -> deliver)
  Unconditional-when-playing (same `if (pulses > 0)` gate the pre-fix deliver() call already used, so it
  never fires on an idle/parked tick -- QT-5 idle-parking invariant is unchanged):
    + 1x cumulativeInjected.addAndGet(...)                    ~12 ns   (measured above)
    + 2x AtomicLong/.get() volatile reads at top of deliver() ~ 2-4 ns each (cheaper than addAndGet; not separately benched, upper-bounded by the CAS-based addAndGet number above)
  Per STEP_COUNTER feed (bounded -- see below), only when that feed exists:
    + 1x Runnable alloc (handler.post)                        ~8 ns    (measured above)
    + 1x reflective SensorEvent alloc (newCounterEvent)       ~22 ns   (measured above, identical pattern to the pre-existing STEP_DETECTOR path)

  TOTAL new cost, both feeds active, 1 pulse this tick: ~12 + 4 + 8 + 22 ~= 46 ns
  vs. 500,000,000 ns tick budget (TICK_MS=500, unchanged)      -> ~9.2e-6 % of one tick period
  vs. design.md budget ":stephook ... <1% of one core"         -> ~7-8 orders of magnitude under budget
  Comparison to the ask's "<= existing per-tick cost" framing: the STEP_DETECTOR path alone already pays
  1x Runnable + Nx(pulses) reflective-event-allocs per tick (~30-50 ns typical N=1-2); the new STEP_COUNTER
  cost (~30 ns for 1 feed) is the SAME ORDER OF MAGNITUDE, not a multiplicative increase -- PASS vs. budget.

  grep of every '+' line in the diff for Thread(/Executor/Timer/new Handler/Handler( -> 0 matches.
  startDriver()'s single `Thread{...}.apply{isDaemon=true}.start()` is UNCHANGED by the diff (not in any
  +/- hunk) and is still gated by the pre-existing `driverStarted` AtomicBoolean.compareAndSet(false,true)

  captureCounterBaseIfNeeded()'s sm.registerListener(reader, counter, SENSOR_DELAY_FASTEST) is a standard

  construct a java.lang.Thread. It is called from attach() (a listener-(re)registration event), NEVER from
  the 500ms tick loop, so it has zero recurring per-tick cost.

BASE-READER ONE-SHOT CHECK
  Guard `if (counterBase.get() >= 0L || baseReader != null) return` precedes any allocation/registration,

  return). The reader's own onSensorChanged unregisters itself (`sm.unregisterListener(this)`) on its
  first callback -- confirmed one-shot by inspection, not merely by naming.
