· **v1.7** — **per-preset lane spacing** (user 2026-07-02). Standing def. of an *optimal route*: (1) start amid many big flowers, (2) pass the most **distinct** nearby big flowers, (3) **open** (start ≠ end OK). Spacing is now **measured per-city** (widest gap-free) and baked per preset — the old ≤1000 m (2×reach) cap was too tight for dense cores where **connector deadhead, not ring spacing, bounds coverage**. Hence per-city, per-intended-length measurement. AC-24(a) spacing bound revised; proof in `proofs/walk-sim_system_quality_pass_preset-spacing.md`.

Length is measured too — `sweepRoute` retraces past an area's fresh-street capacity, so the longest gap-free clean route varies per preset (Shibuya 6, Ueno 16, Chuo-ku/Seoul 12, Odaiba 5, Xinyi 10, rest 20 km). All remaining 10 presets satisfy AC-24(b); Chuo-ku (~11%) is fine. Sequential "All areas" keeps its own total duration (unchanged).

Tighter spacing does NOT increase flowers passed (OLD's wider spiral reaches a larger disc that cancels its gaps). **Tiebreak (user: "prefer the shorter time span"):** a length/time sweep shows 500 m reaches the *same* coverage in less walk time (partial coverage clearly faster: ~1700 locations in ~82 min vs ~106 min), so **Ueno default → 500 m / 10 km** (was 850 m / 16 km). · **v1.9 rollout — ALL presets standardized to 500 m / 10 km** (user chose "Option A" 2026-07-08, after seeing the honest tradeoff). On-device spot-check (Roppongi/Osaka/Seoul) confirmed each lands in a flower-dense field. `LocationsSpacingTest` now pins every preset = 500/10.

## Problem / intent
A **personal tool on one rooted device** (Pixel XL, Android 10) that **simulates a human walking real roads** for a user-chosen duration, and makes **Pikmin Bloom credit both the distance *and* the step count** — with the phone sitting still.

**Route goal (v1.4; reach 500 m per v1.5):** maximize **distinct big flowers per session**. A flower is harvestable within **~500 m** of the avatar (one pass sweeps a ~1000 m corridor), so the route must continuously sweep **new** ground — an outward spiral centred on the start pin (assumed mid-cluster) — not cover every street, and never lap while novel ground remains.

Two cooperating parts (detailed split deferred to design / Gate 2):
- a **controller app** — generates a road-snapped random walk and plays it back as a realistic **location** stream (standard Android mock, v1);
- the proven **LSPosed step-injection module** (`spike-step-hook`, S1) — fed the controller's live pace so **injected steps match the walked distance**.

## Assumptions
- Device is rooted with Magisk + Zygisk + LSPosed/Vector present; the step module is enabled and scoped to **`com.nianticlabs.pikmin` AND `com.google.android.gms`** (2-process scope — the Weekly-Challenge fix of 2026-07-13; see `design.md` §"Weekly-Challenge fix"). *(Primary device is now the Pixel 7 Pro `cheetah`/Android 17 per the on-device proofs; the original Pixel XL / Android 10 target — memory `target-device-pixel-xl` — predates the GMS scope.)*
- The controller app is the selected **mock-location app** (Developer Options).
- **Road data is fetched on-demand (online) for the area around the start pin** and cached simply; there is no offline multi-area manager (see Out of scope).
- Pikmin Bloom v147 reads steps from an in-process `STEP_DETECTOR` listener and raw **GPS_PROVIDER** location (per prior art + S1 spike).
- Defaults (confirmed at Gate 1): **default start = Shibuya, Tokyo (≈ 35.6595, 139.7006)**; radius R = **800 m**, stride = **0.75 m**, mean speed ≈ **1.3 m/s**, fix rate **1 Hz**.

## Out of scope (v1)
- **Un-flagged location** (`isMock()==false`): v1 uses standard mock (`isMock()==true`, proven to credit distance). Root-level un-flagging is a **planned follow-up**, not v1.
- Offline multi-area download/management; polished Google-Maps UI; a broad API-level matrix (single device / single OS version).
- GMS Activity-Recognition spoofing (S1 proved detector-only injection suffices).
- The hardware servo cradle (rejected).
- Cross-device reproducible seeds; saved/replayable walk history (walks are ephemeral, re-runnable from seed).

## Acceptance criteria (EARS / Given-When-Then)
Each is measurable and falsifiable, and maps 1:1 to a test.

### Walk generation
| ID | Criterion |
|---|---|
| **AC-1** | GIVEN a start pin and duration D, WHEN a walk starts, THE SYSTEM SHALL generate a road-snapped route of length `targetLen = meanSpeed × D`, such that the played duration ∈ **[0.9·D, 1.1·D]**. (D = **active playback time**; user pauses do not count toward D.) *(v1.4: does not apply to closed runs — AC-24e — where D sizes the spiral and playback runs the full closed loop home.)* |
| **AC-2** | THE SYSTEM SHALL keep every generated point within the walk's **duration-derived sweep disc**: fetch/route radius `R(D) = √(laneSpacing·meanSpeed·D/π + r0²) + 300 m`, capped at **2500 m** (v1.6: 2000→2500 so a 20 km spiral fits the disc without shortfalling into re-walk; natural floor ≈ 600 m) (lane spacing default 850 m, first ring r0 = 300 m; code-config + adb-tunable, not a v1 UI field). *(v1.4: was fixed 800 m — the sweep sizes its area to the duration.)* |
| **AC-3** | THE generated walk SHALL NOT make an **avoidable** reverse (bearing change **> 150°**) at a node of degree **> 1** — it MUST take a ≤150° non-backtracking in-radius edge whenever one exists. **Forced** reversals are exempt: degree-1 dead-ends, the radius boundary, and **functional dead-ends** (a degree>1 node whose only non-backtracking in-radius edges are all >150°). *(Clarified 2026-06-30; v1.4: scoped to the loop=false random walk — the sweep route's spiral-leg joints and cul-de-sac exits are functional dead-ends under the same exemption.)* |
| **AC-4** | Every generated point SHALL lie on a **foot-walkable** road edge within **0.1 m** (road-snapped), using only foot-accessible highways — excluding `motorway`/`trunk`, `foot=no`, `access=private`. (WALKABLE filter MUST be applied at the use-site, not merely defined — prior-art regression.) |
| **AC-5** | GIVEN identical (seed, start, D, graph), THE SYSTEM SHALL generate an **identical** route (within-device determinism). |
| **AC-6** | WHEN a walk starts, THE SYSTEM SHALL snap the start pin to the nearest **connected** walkable node within **≤ 50 m**; IF none, THEN a clear error (no zero-length walk). |
| **AC-24** | *(v1.4; reach 500 m per v1.5)* GIVEN big flowers are harvestable within **~500 m**, THE loop-mode route SHALL be an outward **harvest sweep** sized to the duration: (a) lane spacing chosen **per-city as the widest gap-free value** (default **850 m**; on dense cores measured up to **~1200 m** — where connector deadhead, not ring spacing, bounds coverage, so wider rings sweep more distinct ground gap-free; v1.7, see `proofs/walk-sim_system_quality_pass_preset-spacing.md`), the binding constraint being **no harvest gaps** — ≥ **95%** of graph nodes inside the swept disc (max route radius − 300 m) lie within **500 m** of the route; (b) ≥ **80%** of walked metres on **new ground** (not within 100 m of route walked ≥ 500 m earlier); (c) NO repeat lap while the spiral can still reach unswept ground — once the spiral exits the fetched graph, residual off-spiral pockets (bounded by (a)'s 5% tolerance) are foregone rather than chased, and the sweep is retraced to fill remaining time; (d) deterministic for identical (graph, start, budget, spacing); (e) The **default is the OPEN spiral** (v1.6: max distinct flowers, ends at the outer edge — closing costs a ~2.5 km return leg that harvests nothing). WHEN a closed run is requested (`close_s`), the **played walk** SHALL end at its start: `D` sizes the outbound spiral, the shortest path home is appended, and the whole closed loop is played in full (played time tracks the loop length, so **AC-1's [0.9D,1.1D] does not apply to closed runs**; the return leg is exempt from (b)). |

### Motion realism
| ID | Criterion |
|---|---|
| **AC-7** | WHILE playing, THE SYSTEM SHALL emit fixes at **1 Hz** with consecutive displacement **≤ 2.5 m/s × Δt + 2 m** (no teleport). |
| **AC-8** | THE SYSTEM SHALL keep non-paused speed ∈ **[0.8, 1.8] m/s** with acceleration **≤ 0.5 m/s²**, and emit **≥ 1 pause** per ≥10-min walk. |
| **AC-9** | THE SYSTEM SHALL report `bearing` within **±10°** of movement direction and `speed` within **±0.1 m/s** of `Δdistance/Δt`. |
| **AC-10** | THE SYSTEM SHALL apply horizontal-offset noise with stddev ∈ **[1, 15] m**, reported `accuracy` ∈ **[5, 50] m**, and **lag-1 autocorrelation > 0.5** (correlated, not white). *(v1.3: floor lowered 2→1 m — on-road-snap priority per user request 2026-06-30; the engine uses ~1.5 m so the avatar hugs the rendered street rather than drifting off it.)* |

### Location injection (standard mock — v1)
| ID | Criterion |
|---|---|
| **AC-11** | WHEN playing AND selected as mock app, THE SYSTEM SHALL deliver moving fixes to **`LocationManager` GPS_PROVIDER** (Pikmin's source), each `isMock()==true`, and **Pikmin SHALL credit the accruing distance** (≥1 observable reward increment over a short walk). |
| **AC-12** | THE SYSTEM SHALL mock **gps + network + fused consistently** (drive fused via `setMockMode(true)`), so no consumer fuses a **stale real fix** (prior-art teleport leak); verified by `dumpsys location` agreement (same coord + mock flag). *(v1.4: THE SYSTEM SHALL also push a **holding fix at the start pin before the graph fetch** — between engaging mock and the first route fix the providers hold no location, so the consumer reads the last REAL fix during the fetch and jumps to the real location; live-fetched cities gap seconds, baked Shibuya none. On-device proven 2026-07-01.)* |
| **AC-13** | Emitted `Location`s SHALL set `time = currentTimeMillis()`, `elapsedRealtimeNanos = SystemClock.elapsedRealtimeNanos()` (real device uptime), `accuracy > 0`, and speed/bearing accuracy — so fixes are accepted. |
| **AC-14** | WHILE playing, THE SYSTEM SHALL run a **foreground service** (`location` type) + ongoing notification; fixes keep flowing while backgrounded / screen-off. |
| **AC-15** | WHEN D elapses OR the user stops, THE SYSTEM SHALL stop emitting and **restore real providers** (`removeTestProvider` / `setMockMode(false)`); the consumer then sees real (`isMock()==false`) fixes. |
| **AC-16** | WHEN the app is NOT the selected mock app, THE SYSTEM SHALL show a **persistent banner within 2 s** and not silently behave as if working. (Detected reactively via `SecurityException` on `addTestProvider`.) |

### Step injection (proven mechanism — S1)
| ID | Criterion |
|---|---|
| **AC-17** | WHILE playing, injected steps SHALL be **credited by Pikmin** such that its step count increases at pace ≈ **walked distance / stride** (stride default **0.75 m**) within **±10%** over a ≥5-min walk, phone motionless. |
| **AC-18** | Step injection SHALL be **active only while a walk is playing**; on pause/stop it SHALL cease **within 2 s** (no phantom steps when idle). |
| **AC-19** | THE injected step pace SHALL **track the current simulated speed** (a faster segment yields proportionally more steps/min), reflecting a speed change **within 5 s**. |

### Control & status (streamlined)
| ID | Criterion |
|---|---|
| **AC-20** | THE SYSTEM SHALL provide **start / pause / resume / stop**, each effective within one update interval (1 s). |
| **AC-21** | THE SYSTEM SHALL let the user pick a **start location** via a **lightweight OSM map pin (osmdroid — no Google API key)**, defaulting to **Shibuya, Tokyo**, and set **duration** (and optional pace/speed) before starting. |
| **AC-22** | THE SYSTEM SHALL show, in its **own UI**, live **speed, distance, steps, elapsed, remaining, and progress**. |
| **AC-23** | IF the app is not the selected mock app (reactive), OR IF — while Pikmin is foregrounded — the step module has **not queried `PaceProvider` within N s** (inferred "module not enabled/scoped"), THE SYSTEM SHALL show a **clear setup error** naming the missing prerequisite, not fail silently. |
